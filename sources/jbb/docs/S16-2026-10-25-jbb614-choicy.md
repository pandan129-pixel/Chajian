## 3. Choicy（`opa334/Choicy`，开源）研究

**架构**：不是“藏 tweak”，而是在 `dlopen` 层做门禁。

- 极小 dylib `"   Choicy"`（名字前三个空格）常驻所有进程；
- hook `dlopen` / `dyld::dlopen`，按 prefs 拦截后续 tweak；
- prefs：`globalDeniedTweaks` + `appSettings[bundleid]`
  （`tweakInjectionDisabled`、`allowDenyMode`、`deniedTweaks`、`allowedTweaks`）；
- 环境变量覆盖：`CHOICY_DENIED_TWEAKS_OVERRIDE` 等；
- 白名单永远放行自身与关键 tweak。

**采纳**：per-process 主开关、环境变量硬开关、prefs 驱动（不依赖 filter 重装）。
**未采纳**：hook `dlopen`（加载器职责，jbb 是被加载方，加一层只增风险）。

## 4. 性能数据（微信，同一进程 pid 5081）

| 操作 | 6.9 | 6.10 | 6.14 |
|---|---|---|---|
| 豁免路径 `stat` | 12,885 ns/op | 11,746 | **11,604** |
| 越狱路径 `stat`（被拦） | 8,416 | 5,910 | **4,909** |
| 隐藏镜像 `dladdr` | 7,048 | 87 | **30** |

说明：绝对值受设备负载影响，看相对趋势；`dladdr` 是 6.9 的最大隐性成本（每次调用遍历全部镜像的 load command）。

**2026-10-25 修正（重要）**：上表“`stat`”一行的绝对值**不是 jbb 的开销**。那两条路径
（SystemVersion.plist / 一个不存在的 Preferences 文件）都会真的进入内核，测到的是
「stat 系统调用 + App 沙箱 + roothide 自己的路径重写 + 设备负载」。
后续用 CPU 时间重测：被拦截的 `/var/jb`（不产生系统调用，纯 jbb 路径）约 **0.9 µs/op**；
真实允许路径 19–44 µs/op，其中 jbb 只占很小一段。

因此：
- 要衡量 jbb 自身成本，看 `blocked`（/var/jb）这一项，或做同进程 jbb 开/关 A/B；
- 6.9→6.14 的 -42% 反映的是**钩子内部逻辑**（豁免/前缀/token）的优化，不是系统调用；
- 不要在真机上用墙钟（`mach_absolute_time`）做微基准：进程被挂起时会把挂起时间算进去。

## 4.1 token 匹配开销（2026-10-25 追加，微信 pid 5233，纯 CPU 时间）

| 路径 | 命中位置 | ns/op |
|---|---|---|
| `/var/jb` | fast-prefix 表（不进 token 循环） | **1,272** |
| `/zz/roothide` | core token 靠后 | 9,723 |
| `/zz/substrate` | core token 最后 | 9,092 |
| `/zz/cycript` | extra 层（当时关闭 → 真实 syscall） | 13,135 |

结论：

- **fast-prefix 早退是最有效的**：1.3 µs vs 9 µs；
- token 循环本身是主要成本，且与命中位置几乎无关（9.0–9.7 µs），说明是逐条 `strstr` 扫表；
- `extraTokens` 多 19 条 → 未命中时多扫约 19 条，按上表估算 **+6~7 µs**，所以默认关闭是对的。

据此实现了 **6.15**：用「首字节锚点索引」替代 N 次 `strstr`（一次遍历路径，只在首/次字节匹配时做 `strncmp`）。

**已验证（微信 pid 5512）**：

| 路径 | 6.14 | 6.15 | 变化 |
|---|---|---|---|
| `/var/jb`（fast-prefix） | 1,272 | **990** | -22% |
| `/zz/roothide`（靠后命中） | 9,723 | **2,834** | **-71%（3.4×）** |
| `/zz/substrate`（最后命中） | 9,092 | **3,127** | **-66%（2.9×）** |
| `/zz/cycript`（extra 关，走 syscall） | 13,135 | 7,612 | -42% |

功能回归同时通过：`csops=0x22007001`、`dyld 931/0/0/931`、路径全 ENOENT。

补充的基准方法坑：

- 必须用 `CLOCK_THREAD_CPUTIME_ID`；墙钟会把挂起时间算进去，`CLOCK_PROCESS_CPUTIME_ID` 会把 App 其他线程算进去；
- 同一个 dylib 对同一进程 `opainject` 两次不会重跑 constructor（dlopen 返回已有 handle），换 build 需要重启目标进程。

## 5. 验证方法（重要，可复用）

TweakLoader 对新增 dylib 有缓存，且锁屏时 App 不在前台，延迟探针不会执行。可靠做法是**直接注入已在前台的进程**：

```sh
JB=$(/usr/bin/jbroot)
T="$JB/usr/lib/TweakInject"

# 1) 加 trustcache（必须用 jbroot 前缀路径）
jbctl trustcache add "$T/probe.dylib"

# 2) 直接注入目标 pid
opainject <pid> "$T/probe.dylib"
```

两个坑：

1. `jbctl` / `opainject` 会把 `/var/jb/...` 按 vroot 重定向，**必须传 `$(jbroot)` 前缀的真实路径**，否则报 `Can't access passed dylib`；
2. `jbctl update basebin` 同理，传 `/var/mobile/...` 会报 file not found。
