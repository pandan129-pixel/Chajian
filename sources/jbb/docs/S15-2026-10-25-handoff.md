## 3. jbb 版本演进（本会话）

| 版本 | 改动 | 状态 |
|---|---|---|
| 6.1 | 移除 SSH/Frida 路径与端口 hook（用户要求） | 稳定 |
| 6.2 | 尝试 per-app profile，引入 `backtrace_symbols_fd` | **加载失败**（iOS 16 libSystem 不导出该符号） |
| 6.3 | 去掉 backtrace，profile 可用 | 稳定 |
| 6.4 | 加信号崩溃记录（SIGSEGV/BUS/ILL/TRAP/ABRT/FPE） | 稳定 |
| 6.5 | 加 `kill` hook | 稳定 |
| **6.6** | **dyld 一致索引映射 + csops hook** | 当前部署 |

### 6.6 的两个核心修复

**(a) dyld 枚举一致性**（旧版缺陷）：
旧版把所有隐藏镜像名替换成同一个 `/usr/lib/libSystem.B.dylib`，导致
`_dyld_image_count()=934` 但唯一路径只有 922（12 个重名）→ 可直接判定篡改。

6.6 改为同一张索引映射表，四个 API 全部对齐：
`_dyld_image_count` / `_dyld_get_image_name` / `_dyld_get_image_header` / `_dyld_get_image_vmaddr_slide`
隐藏镜像从列表整体移出，索引重排。

实测（微信）：`count=922, dup=0, unique=922, null=0, susp=0, stable=1`。

**(b) csops**：
roothide 3.x 默认用 `CS_GET_TASK_ALLOW` + `DYLD_INSERT_LIBRARIES` 注入。
实测微信注入后：`flags=0x32007004, GET_TASK_ALLOW=1, DEBUGGED=1`。
6.6 hook `csops` / `csops_audittoken`，对自身查询清掉这两个位：
`0x22007000, GET_TASK_ALLOW=0, DEBUGGED=0`。

源码：`jb-bypass/src/jbb_v66.c`

### per-app profile

配置：`/var/mobile/Library/RootHide/jbb_profiles.plist`（root:wheel 644）
结构：`{ "<bundleid>": { file, dyld, name, sysctl, ptrace, env, ppid, objc, csops, diag } }`
无条目 = 全开。profile 生效后会在 App 的 Documents 写 `jbb_v62_profile` 标记（内容即各开关值）。

## 5. QQ 专题

### 现象与定位
- 注入 jbb → QQ 运行中随机闪退（滑历史记录时最容易触发）
- **无 `.ips`、无 exit/abort、无信号记录、无 kill 记录** → 无法捕获，判定为 SIGKILL / raw syscall 退出
- QQ 自己写 `Library/N.startcrash` 标记
- 二分结果：
  - `objc`（NSFileManager IMP 替换）→ **必崩**
  - `sysctl` → 未单独确认（Step A 组合崩过）
  - `dyld`/`name` → 关闭（怀疑数值一致性）
  - `ptrace`、`file`、`env` → 稳定

### 结论
QQ 反作弊会检查 **Method 的 IMP 是否指向 dyld 缓存原实现**。改 IMP 一定被看到，没有干净绕过。
`objc` 对 QQ 也是冗余的：`NSFileManager` 底层是 `stat/open/readdir`，已被 file hook + RootHide vroot 覆盖。

### 最终配置（`.20` 当前）

```xml
<key>com.tencent.mqq</key><dict>
  file=true  env=true  ptrace=true  ppid=true
  dyld=false name=false sysctl=false objc=false csops=false diag=false
</dict>
```

### NTQQ 防撤回
- 已打成 deb：`com.pandan.ntqq 1.6.2`（dylib 2.58MB，来自 `.28` 备份）
- `.20` 上**加载正常**，但防撤回不生效（其它功能有效）→ 判断为该 tweak 与当前 QQ 版本 hook 点不匹配
- 源里最新也是 1.6.2，无法简单升级

## 6. 大麦专题（cn.damai.iphone）

| 测试 | 结果 |
|---|---|
| 黑名单（完全不注入） | 仍「访问拒绝」 |
| 注入 + jbb 全开 | 探针全项 PASS，但仍拒绝 |
| 启动期 stat/open/access/connect 追踪（1040 条） | 无任何越狱路径检查 |

追踪到的关键点：
- `connect 127.0.0.1:27042`（Frida 端口探测，端口关闭）
- 大量阿里系 IP 443/80 上报（106.11.x / 122.x）
- 抓到 roothide 自身痕迹：`lstat .../libobjc-trampolines.dylib.roothidepatch`（patchloader 探测，非 App 行为）

**结论：服务端风控**（阿里设备指纹/风控 SDK 上报后服务器判定），本地无法用常规隐藏手段解决。

| 工具 | 路径 | 用途 |

| `jbtest7` | `tests/jbtest7.m` | dyld 一致性（count/unique/dup/stable） |

| `damaitrace` | `tests/damaitrace.m` | hook stat/open/access/connect，记录 App 启动期检查 |

编译方式（Mac）：

```sh
SDK=$(xcrun --sdk iphoneos --show-sdk-path)
clang -arch arm64 -arch arm64e -miphoneos-version-min=15.0 -isysroot "$SDK" \
  -fobjc-arc -O2 -dynamiclib -framework Foundation -o X.dylib X.m
codesign -f -s - X.dylib
```

设备端注意：
- 传文件用 `ssh 'cat > /path' < local`（该设备新 sshd 的 `scp` 会卡住）
- 必须**解锁**再 `uiopen`，锁屏时构造函数里的写入会被拦（会被误判为「没生效」）
- 重启 App 要用 PID：`pid=$(launchctl list | grep -F <bundle> | cut -f1 | head -1); kill -9 $pid`
  `killall` 对部分 App 不生效（曾导致大量误判）
- `remotemods` 需要 `platform-application + task_for_pid-allow + no-sandbox`，用设备上的 ldid 签名

## 11. v6.9（2026-10-25 晚，最终部署）

对 6.6 的三条外部评审逐一核实：

| 问题 | 核实 | 处理 |
|---|---|---|
| `csops_audittoken` 路由到 4 参数实现（`o_csops2` 从未使用） | 属实 | 6.9 拆成正确 5 参数 hook，各自调自己的 original |
| `dladdr` 对隐藏镜像「假名字 + 真基址」 | 属实 | 6.9 改为：名字/基址都指向可见的 `libSystem`（基址在可见列表内） |
| `/TweakInject/*.dylib|plist` 豁免 | 属实（MSHook 副作用，需豁免才能继续加载 tweak） | **未修**，属已知限制；要彻底去需换 rebind 形态（basebin 版） |

**重要回归教训**：最初按建议让 `dladdr` 对隐藏镜像直接 `return 0`，结果微信 1–2 秒后必崩
（微信对隐藏地址调 dladdr 后不检查返回值直接用）。必须 `return 1` 且基址合法。

**单架构问题**：arm64e-only 的 dylib 无法注入 arm64 的 App Store App
（实测微信进程能起，但 jbb 完全不加载，无任何标记）。
最终产物必须是 **arm64 + arm64e 双架构**（245 KB）。
